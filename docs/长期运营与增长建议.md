## 二、内容策略（P0，优先级高于一切技术优化）

技术只决定「来了之后体验如何」，内容决定「有没有人来、会不会再来」。

### 2.1 把垂直方向讲清楚

你写的是 STM32 / 嵌入式，这是**搜索价值很高**的领域：问题具体、答案可复用、从业者会主动搜。

建议：

1. **首页第一屏就说明你是谁**。现在站点标题是「小马哥个人博客」，建议改成能体现专业方向的形式，例如
   「小马哥的嵌入式笔记 · STM32 / 硬件 / 踩坑记录」。搜索引擎和首访者都能立刻判断「这个站跟我有没有关系」。
2. **做专栏（系列）页**。STM32N6 已经写到 `01`–`05`，这是最有价值的资产。建议在主题里加一个「系列」页面，
   把同一系列的文章按顺序列出。Hexo 侧可用 `categories` + 自定义页面模板实现，或直接写一个静态汇总页。
3. **给教程类文章统一结构**。现在各篇结构差异很大。建议模板：

   ```
   一句话结论（TL;DR）
   前置条件（芯片/工具链/库版本）
   步骤（每一步一张图或一段代码）
   踩坑记录（这一节最值钱）
   完整工程 / 代码仓库链接
   参考链接
   ```

   读者和搜索引擎都偏爱这种结构；「踩坑记录」是最容易被别人引用、最容易被搜索命中的部分。

### 2.2 让旧文继续产生价值

技术博客的复利来自**旧文被反复搜索到**。

- 用 front-matter 的 `updated` 明确标注修订日期（当前用 `updated_option: mtime`，改图改字就会变，建议改成手写 `updated`）。
- 每年挑 5 篇高流量文章做一次「翻新」：补新版本号、补失效链接、补 2026 年的做法。
- **别删旧文**。技术过时了就在开头加一句「本文基于 STM32CubeMX 6.x，新版界面略有不同」，比删除有价值得多。

### 2.3 写作节奏

- 稳定比高产重要：**每月 2 篇** 持续一年，远胜一次性 20 篇然后停更半年。
- 一篇长文拆成系列比一篇超长文更容易被搜索到（每篇都能独立命中一个长尾问题）。

## 三、可发现性（SEO）：把已经有的用好

### 3.1 立刻能做的（P0）

| 动作 | 怎么做 | 说明 |
| :--- | :--- | :--- |
| 提交搜索引擎 | 分别在 **Google Search Console**、**Bing Webmaster Tools**、**百度搜索资源平台** 添加站点并提交 `sitemap.xml` | 现在站点已有验证文件（`google*.html`、`BingSiteAuth.xml`、`baidu_verify_*.html`），说明验证做过，但**提交 sitemap 与查看收录状态**是另一件事，必须做 |
| 检查收录 | 在三个平台用 `site:blog.556106.xyz` 看收录数量 | 如果 Google 收录远多于百度，说明百度抓取有问题，优先处理百度 |
| 规范链接（canonical） | 在主题 `layout/_partial/head.ejs` 里加 `<link rel="canonical" href="...">` | **重要**：同一页面可能通过 `xxx.github.io` 和 `blog.556106.xyz` 两个域名访问，不加 canonical 会被判重复内容、分散权重 |

### 3.2 结构化数据（P1，收益明显）

在文章页 `<head>` 注入 JSON-LD，让搜索结果带上作者、日期、封面图，点击率通常有可感知提升：

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "<%= page.title %>",
  "datePublished": "<%= page.date.toISOString() %>",
  "dateModified": "<%= page.updated.toISOString() %>",
  "author": { "@type": "Person", "name": "littlehorsebrother" },
  "image": "<%= full_url_for(page.cover || theme.cover.first) %>",
  "mainEntityOfPage": "<%= page.permalink %>"
}
</script>
```

同时补上 Open Graph（`og:title` / `og:description` / `og:image`），**分享到微信/QQ/知乎时会显示卡片**而不是一条光秃秃的链接。现在没有配置，分享出去很难看。

### 3.3 内容分发（P1，涨粉最快的一步）

个人博客流量大头往往**不来自搜索，而来自平台导流**：

| 平台 | 适合发什么 | 注意 |
| :--- | :--- | :--- |
| 知乎 | 回答具体问题，末尾附原文链接 | 别整篇搬运，写「精简版 + 原文链接」 |
| 掘金 / CSDN | 技术长文 | 同步全文时**必须设 canonical 指向博客**，否则 SEO 权重被判给平台 |
| B 站专栏 | 与视频配套的图文 | 你有视频素材的话性价比很高 |
| GitHub | 项目 README 里放博客链接 | 技术人流量最精准的来源 |

> 关键：**平台发精简版或完整版 + canonical 回指原文**。既拿流量，又不在 SEO 上吃亏。

### 3.4 技术性 SEO 细节

- 文章 URL 目前是 `post/20260319163436.html`（时间戳）。**好处**是稳定；**坏处**是完全不含关键词。
  如果愿意，可以改成 `post/:year/:title.html` 这类「含拼音标题」的形式 —— 但对已发布的 37 篇是破坏性变更（旧链接失效），
  建议**只在新建文章时启用**，或干脆保持现状（现在这样也不算错，靠内容与内链取胜）。
- `robots.txt` 现在是好的（放行内容页、屏蔽静态资源、声明 sitemap）。保持。
- 每个分类/标签页是天然的落地页，**给重点分类写一段介绍文字**（现在只有列表），能明显提升该页的搜索表现。

## 四、性能：目前最该动手的地方

### 4.1 实测问题

```
首页引用的 JS/CSS：919 KB / 25 个文件
  materialize.min.js      186 KB
  materialize.min.css     142 KB
  awesome/all.min.css      99 KB   （Font Awesome 全量图标）
  jquery-3.6.0.min.js      87 KB
  APlayer.min.js           58 KB   （音乐播放器，music.enable: true）
  lightgallery-all.min.js  55 KB
  animate.min.css          52 KB
  dark.css                 49 KB
  matery.css               46 KB
  aos.css                  25 KB
  masonry.pkgd.min.js      24 KB
  ...

文章页额外：655 KB
  prism.min.js            568 KB   ← 单个文件最大
  crypto-js.min.js         47 KB
  social-share.min.js      24 KB
  prism.min.css            14 KB
  tocbot.min.js            11 KB
```

**结论**：一个文章页在加载任何图片之前，就要先下载约 **1.5 MB** 的 JS/CSS。移动端 4G 下这通常是 2–4 秒。

### 4.2 收益最大的四件事（P0）

| 动作 | 预计效果 | 怎么做 |
| :--- | :--- | :--- |
| **关掉音乐播放器** | −58 KB JS + 一个播放器实例 | 主题 `_config.yml` 里 `music.enable: false`（当前是 `true`） |
| **Prism 按需加载** | −568 KB → 约 −500 KB | 只打包用到的语言（现在全量）；或改成「点击后加载」；最简单是换 CDN 版本并 `defer` |
| **Font Awesome 子集化** | −99 KB → 约 −20 KB | 只保留用到的图标；或用 iconfont 替代 |
| **图片懒加载 + 固定尺寸** | 首屏更快、CLS 更稳 | 主题的 marked 渲染加 `loading="lazy"`，并在 `<img>` 上补 `width`/`height` |

> **✅ 以上四项已于 2026-10-18 全部落地，实测结果：**
>
> | 指标 | 优化前 | 优化后 | 降幅 |
> | :--- | ---: | ---: | ---: |
> | 首页引用 JS/CSS | 919 KB / 25 个 | **845 KB / 22 个** | −8% |
> | 文章页引用 JS/CSS | 1574 KB / 33 个 | **935 KB / 27 个** | **−41%** |
>
> 实现方式：音乐播放器 music.enable: false；Prism 客户端脚本整段移除（构建时已预高亮，
> 样式表保留）；图片懒加载与宽高标注由主题插件 scripts/lazy-images.js 完成。
>
> **Font Awesome 子集化试过又回滚了**：裁剪后 CSS 从 99 KB 降到 11 KB，但它是新文件名，
> 部署或 CDN 缓存只要有一环没同步，页面引用了它而文件 404，全站图标会一起消失。
> 个人博客承受不起这种「一个文件拖垮全站」的脆弱性，宁可多 88 KB 也要稳。
> 这件事的启示写在 §十二「不建议做的事」之外：**优化要挑不会因为部署失误而放大成故障的项**。

### 4.3 再进一步（P1）

- **把静态资源挂 CDN**：主题 `jsDelivr.url` 现在是空的（走本地）。填上 CDN 地址能让海外访问明显变快。
  注意：国内访问 jsDelivr 不稳定，建议用 **国内可达的 CDN**（如自建或 Cloudflare）。
- **Consider Cloudflare**：前置一层 CDN，免费套餐就能提供缓存、压缩、HTTP/3，并且能挡住部分扫描流量。
  代价是 DNS 要托管过去，配置约 15 分钟。
- **图片用现代格式**：`tools/optimize-images.ps1` 现在输出 JPEG。若能接受，加一步生成 WebP（同画质约小 25–35%），
  用 `<picture>` 兜底旧浏览器。
- **首屏只保留必要 CSS**：`dark.css` 49 KB 在未启用暗色模式时不该全量加载。

### 4.4 怎么验证

- 用 **PageSpeed Insights**（移动端）跑一次首页和一篇长文，记录 LCP / INP / CLS。
- 目标（Core Web Vitals 的「良好」线）：**LCP < 2.5s、INP < 200ms、CLS < 0.1**。
- 每做一项优化就重测一次，**别凭感觉**。

## 八、推广：让更多人看到

按「性价比」排序：

1. **GitHub Profile README**（30 分钟）：在你的 GitHub 主页 README 里放博客链接，来你仓库的技术人会点。
2. **把文章里的代码放到独立仓库**，README 里注明「详细教程见博客」。仓库的 star 会持续给你带流量。
3. **知乎回答**：搜「STM32xxx 怎么配置」，认真回答并在末尾附链接。一个高赞回答能带来持续数月的新访客。
4. **参与社区**：立创开源硬件平台、电子发烧友、ST 官方社区、各种嵌入式 QQ/微信群里分享。
5. **交换友链**：现在友链页是空的，可以主动找同量级的博主互加。
6. **RSS 被订阅**：把 RSS 地址放到 GitHub README 和各平台签名里。

> 不要做的事：买流量、刷访问量、到处贴无关链接 —— 短期有点数据，长期毁掉站点在搜索引擎里的信誉。

## 十、用数据驱动，而不是凭感觉

### 10.1 建议关注的指标（别贪多）

| 指标 | 在哪看 | 说明 |
| :--- | :--- | :--- |
| 搜索曝光 / 点击 / 点击率 | Google Search Console、百度资源平台 | 点击率低说明标题和摘要不够吸引人 |
| 热门落地页 | 同上 | 找出「意外受欢迎」的文章，围绕它写系列 |
| 访问量与来源 | Umami / 百度统计 | 判断哪个平台导流最有效 |
| Core Web Vitals | PageSpeed Insights | 每次大改后测一次 |
| 订阅数 | RSS / 邮件列表后台 | 最真实的「铁杆读者」指标 |

### 10.2 节奏

- **每月**：看一次搜索后台，挑 1 篇表现好的文章做续集。
- **每季度**：跑一次 PSI，做一项性能优化；检查死链；更新 2–3 篇旧文。
- **每年**：审视一次主题与技术栈，决定是否重构（**不要频繁换主题**，每次换都会丢一批链接和样式细节）。

## 十二、明确不建议做的事

1. **不要频繁换主题**。每次换都可能丢链接、丢样式、丢已做的优化，收益却是一次性的新鲜感。
2. **不要堆插件**。每多一个插件就多一份升级负担，本项目已经从 17 个依赖精简到 14 个，别走回头路。
3. **不要开启花哨特效**（雪花、彩带、鼠标星星、背景音乐自动播放）—— 对技术读者是减分项。
4. **不要把文章全文同步到多个平台却不设 canonical** —— 等于把自己的搜索权重送人。
5. **不要为了「看起来更新」而修改文章日期** —— 读者和搜索引擎都会发现。
6. **不要盲目升级大版本**（hexo 8 的教训：构建能过，但代码高亮样式全乱）。
7. **不要把大文件（视频、高清原图）提交进仓库** —— 仓库会不可逆地膨胀。

## 十三、一句话总结

> **内容垂直 + 结构统一 + 首屏够快 + 分发出去 + 有订阅和评论** —— 这五件事做到，
> 一个个人技术博客就能长期健康地跑下去；其余都是锦上添花。

当前仓库在「结构规范、文档完善、构建健康」上已经做得比多数个人博客好，
接下来最值得投入的依次是：**性能（首屏 1.5 MB 太重）→ 订阅与评论（留住读者）→ 多平台分发（让更多人看到）**。
